# 방송국별 계좌 수집 기기 한 대 제한 패치

이 패치는 전체 서버 교체본이 아닙니다. 기존 앱과 Java 수집기를 교체하지 않습니다.

## 적용 순서
1. Supabase SQL Editor에서 `sql/single_bank_device.sql`을 실행합니다.
   - 기존 중복 연결은 마지막 동기화 시각이 가장 최근인 한 대만 유지합니다.
   - 이전 연결은 state=revoked, enabled=false 처리합니다.
   - 기기 이력과 후원 내역은 삭제하지 않습니다.
   - 연결 교체/승인 API의 DB 변경 자체에 적용되므로, 기존 서버 API와 관리자 앱 연결 경로에도 적용됩니다.
   - 비활성 수집 상태여도 연결은 방송국당 최대 한 대입니다.
2. 기존 저장소의 `public/bank-device-control.html`만 이 파일로 덮어씁니다.
3. GitHub Desktop에서 Commit / Push 후 Railway 배포 완료를 확인합니다.
4. 웹 기기 관리 화면을 새로고침합니다. 연결된 카드만 나타납니다.

SQL 적용만으로 실제 중복 연결은 해결됩니다. 화면 파일은 연결 해제 이력을 목록에서 숨기는 변경입니다.
신규 DB라면 기존 station_bank_devices 테이블 설치가 먼저 필요합니다.
현재 유지된 기기의 기본 크리에이터가 비어 있으면 이름을 선택/입력하고 설정 저장하세요.
연결된 기기가 없으면 앱에서 새 코드를 발급받아 웹에서 승인하고 수집 사용을 켭니다.
새 기기 승인 시 기존 연결은 자동 해제되며 새 연결의 수집 시작은 기존 방식대로 설정 저장이 필요합니다.

같은 모델명을 한 대로 합치는 방식이 아닙니다. 같은 모델의 실제 휴대폰 두 대를 구분할 수 없기 때문에 방송국 연결 상태를 기준으로 제한합니다.
기존 앱은 연결 요청 시 새 연결키를 생성하므로 이력이 늘 수 있지만 동시에 linked 상태인 기기는 한 대만 허용됩니다.
이미 수집·승인된 후원은 유지합니다. 새 연결 이후 해제된 기기의 새로운 요청은 기존 서버의 state 검사에서 차단합니다. 이미 처리 중이었던 요청을 소급 취소하지는 않습니다.

## 검증
PostgreSQL 호환 PGlite에서 중복 정리, 최근 동기화 기기 유지, 새 승인 시 기존 연결 해제, 다른 방송국 유지, 반복 SQL 적용, 동시 요청 후 유일성, 기기 이력 보존을 확인했습니다.
PGlite의 요청 직렬 처리 검증이며 실제 운영 PostgreSQL의 여러 세션 동시 부하 테스트는 수행하지 않았습니다.
웹 관리 화면의 스크립트 문법 검사도 통과했습니다.
운영 Supabase 실행과 Railway 배포는 사용자가 해야 합니다.

관리 화면 파일은 이 대화에서 제공한 V5 서버 기준입니다. 다른 곳에서 관리 화면을 별도로 수정했다면 전체 HTML을 덮어쓰기보다, 기존 load() 함수의 data.devices를 state==='linked'로 필터하는 변경만 반영해도 됩니다.
