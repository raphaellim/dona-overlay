# 방송 오버레이 · Supabase → Neon 이전 안내

이 패치는 기존 디자인과 업무 기능을 유지하면서 일반 PostgreSQL 연결을 추가합니다.
실제 DB 이전은 아직 실행하지 않았습니다. 첨부 ZIP에는 운영 DB 백업이 없습니다.

## 확인된 내용

- 서버의 DB 처리는 서버 측 Supabase 클라이언트에 모여 있습니다. 브라우저에 Neon 비밀번호를 넣을 필요가 없습니다.
- `settings` 1번 행은 여러 방송국과 과거 방송 설정을 함께 보관합니다. 화면·인증 이후 설정을 조회할 때 이 JSON을 반복해서 읽는 코드가 있습니다.
- 오버레이는 현재 방송 후원 목록을 다시 읽고 집계합니다. 기존 오버레이 결과 캐시는 1초입니다.
- 승인·수동입력·펀딩·작업 소유권은 SQL 함수로 처리합니다. DB 주소 교체만으로 Neon으로 이전되지 않습니다.
- 가계부 증빙은 Supabase Storage에 저장합니다. 이미지/영상 등 일반 방송 미디어는 기존 서버 `public` 폴더에 있습니다.
- 화면에서 전송량은 47.6/5GB, DB 용량은 69/500MB였습니다. 반복 조회가 기여할 수 있지만 실제 원인별 사용량은 Supabase Usage에서 확인해야 합니다.

## 이번 변경

1. `DATABASE_URL`을 설정하면 PostgreSQL 드라이버로 연결합니다. 없으면 기존 Supabase 연결을 사용합니다.
2. `settings`, `donations`, `donation_capture_candidates` 조회를 서버 메모리에 기본 15초 보관하고 동일한 동시 조회를 합칩니다. 반환값은 복사해 다른 요청이 저장된 객체를 바꾸지 못하게 합니다.
3. 일반 DB 변경과 후원 반영 SQL 함수 호출 전후에 캐시를 지웁니다. 데이터 변경 요청과 설정 병합 작업은 캐시를 우회합니다.
4. 계정·세션·방송국·기기·토큰 테이블과 작업 잠금 호출은 조회 캐시 대상이 아닙니다. 작업 heartbeat/claim은 매번 DB에서 처리합니다.
5. Neon 모드의 가계부 증빙은 지정한 영구 디렉터리에 보관하고 60초짜리 서명 링크로 내려받습니다. 경로를 설정하지 않으면 증빙 업로드를 거부합니다.

절감률이나 무료 한도 내 운영은 보장하지 않습니다. 짧은 간격에 읽기/쓰기가 모두 많으면 캐시 효과가 작을 수 있습니다. Neon의 전송·컴퓨팅 사용량도 함께 확인하세요.

캐시는 서버 프로세스 하나를 전제로 합니다. Railway Replicas=1로 운영하고, 다른 서버/SQL Editor가 동시에 운영 데이터를 수정하면 `DB_READ_CACHE_SECONDS=0`으로 끄세요. 캐시를 켠 상태에서 외부에서 변경하면 최대 15초 뒤 보입니다.

## 1. 이전 전에 준비

- 이 ZIP의 코드를 새 폴더에 풀고 기존 소스 백업을 따로 보관합니다. `npm install` 후 사용합니다.
- 이 코드는 Supabase 환경변수만 유지한 채 먼저 배포할 수 있습니다. 아직 `DATABASE_URL`을 넣지 마세요.
- [Neon](https://neon.com/)에서 Free 프로젝트를 만들고 기존 Railway 서버와 가까운 지역을 선택합니다. 복원 대상은 **새 빈 DB**로 만드세요.
- Neon Direct 연결 정보를 백업/복원에 사용하고, 서버 운영에는 pooled 연결 문자열을 사용할 수 있습니다.
- Windows PostgreSQL Command Line Tools를 설치합니다. `pg_dump`는 원본 DB 버전 이상이어야 하며, 복원 대상 PostgreSQL도 원본보다 낮은 버전으로 선택하지 마세요.
- 기존 Railway 환경변수를 별도로 보관합니다. ADMIN_PASSWORD, 유튜브/Nightbot OAuth 설정, 암호화 키, 수집기 키와 서버 미디어/이름 매핑 파일을 유지합니다. 암호화 키를 새로 만들면 기존 암호화 토큰을 읽지 못할 수 있습니다.
- 업로드된 소스에는 일부 기존 테스트가 요구하는 SQL 파일이 없습니다. 옛 SQL을 조합해 빈 DB를 만드는 대신 **현재 운영 DB의 public 스키마를 백업해 복원**합니다.

## 2. 최종 백업

방송 중이 아닌 때 진행합니다. 후원 수집 앱, 투네 수집기, 관리 페이지의 입력을 멈추고 원본 Railway 서버도 중지해 백그라운드 작업이 데이터를 바꾸지 않게 합니다. Supabase DB는 켜 둡니다.

PowerShell에서 압축을 푼 서버 폴더로 이동한 다음 실행:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\migration\backup-supabase.ps1
```

화면에 보였던 Supabase Session pooler의 host와 user를 입력합니다. 비밀번호는 `pg_dump`가 별도로 물을 때 PC에서 입력합니다. 채팅으로 보내지 마세요.

성공하면 `migration/supabase-public-날짜.dump`가 생성됩니다. 오류가 한 줄이라도 있거나 파일이 덜 만들어졌으면 다음 단계로 넘어가지 마세요. 파일 생성 자체만으로 성공한 것은 아닙니다. 스크립트가 종료 코드와 백업 목록까지 확인합니다.

서비스 제한 때문에 Session pooler 연결도 막힌다면 이 방법으로 내보낼 수 없습니다. 기존 로컬 백업 유무를 확인하거나, 공식 지원에 데이터 내보내기 접근을 요청하거나, 제한 해제 시점을 기다려야 합니다. 제한된 원본에서 백업 성공 여부는 아직 확인하지 못했습니다.

## 3. 새 Neon DB로 복원

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\migration\restore-neon.ps1
```

위에서 만든 dump 파일, Neon **Direct** host, user, DB 이름을 입력합니다. 비밀번호는 준비 단계와 복원 단계에서 각각 물을 수 있습니다.

이 스크립트는 대상 public 스키마가 비어 있는지 검사하고 확장/정책 참조용 NOLOGIN 역할을 준비합니다. 기존 테이블을 지우지 않습니다. 복원은 단일 트랜잭션으로 수행하고 오류가 나면 중단합니다.

현재 원본에 소스에서 확인되지 않는 Supabase 전용 함수/확장/정책 의존성이 있다면 복원이 실패할 수 있습니다. 오류를 보관하고 연결 변경은 멈추세요. `--clean`으로 원본이나 기존 DB를 지우지 마세요. Neon에서 확장 스키마/역할 생성이 허용되지 않는 경우도 오류를 확인해 개별 대응해야 합니다.

## 4. 데이터 비교

Node.js 22 이상과 `npm install`이 필요합니다. 원본 쓰기를 계속 멈춘 상태로 실행:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\migration\verify-databases.ps1
```

원본/대상의 host, user, DB 이름, 비밀번호를 PC에서 입력합니다. 비교 도구는 public 테이블별 행 수와 내용 지문을 비교하며 데이터를 수정하지 않습니다. 모든 항목이 PASS여야 합니다.

이 비교는 백업 시점 데이터가 같은지 확인합니다. 모든 기능의 동작, SQL 권한과 파일 복사를 대신 검증하는 도구는 아닙니다.

## 5. 증빙과 서버 파일

화면의 Storage 사용량은 0으로 표시됐지만, 실제 증빙 테이블에 파일이 있는지도 확인해야 합니다.

가계부 증빙이 있다면:

- Railway 영구 볼륨 경로에 `RECEIPT_STORAGE_DIR`를 지정합니다. 예: 기존 볼륨이 `/data`라면 `/data/finance-receipts`. 볼륨을 추가할 때는 Railway 비용을 확인하세요. Neon 무료 DB가 서버 볼륨 비용을 대신 부담하지 않습니다.
- 기존 Supabase URL·service role key, 원본 DB 연결의 `SOURCE_DATABASE_URL`, 위 경로를 서버 환경에 설정하고 `node migration/copy-receipts.js`를 실행합니다. 이 도구는 DB의 증빙 메타데이터에 있는 파일을 받아 크기와 SHA-256을 확인합니다.
- 복사 수와 증빙 다운로드를 확인한 뒤에만 Supabase Storage 사용을 종료합니다.
- 이 복사는 호스트의 실제 영구 볼륨에서 실행해야 합니다. PC 임시 폴더에 복사한 파일은 Railway 볼륨에 자동 반영되지 않습니다.

증빙을 쓰지 않는다면 이 경로 설정은 나중에 해도 되지만, 설정 전에는 증빙 업로드를 사용할 수 없습니다.

일반 이미지/영상/알림 파일은 기존 Railway 업로드 폴더를 그대로 유지하고 별도 백업합니다. GitHub 소스 ZIP에 운영 업로드가 모두 있다고 가정하면 안 됩니다.

## 6. Railway 연결 변경과 확인

복원·비교가 끝난 뒤 이 수정본을 배포하고 Railway 변수에 추가:

```dotenv
DATABASE_URL=Neon에서 복사한 서버 연결 문자열
DB_READ_CACHE_SECONDS=15
```

URL은 서버 변수에만 넣습니다. `.env.example`, 브라우저 코드, GitHub에 실제 비밀번호를 넣지 않습니다. Neon 제공 URL의 SSL 설정을 유지하세요. 서버는 자동으로 `.env`를 읽지 않으므로 Railway Variables에 설정해야 합니다.

처음에는 수집기와 자동채팅을 멈춘 채 테스트용 방송으로 아래를 확인합니다.

- 방송국 관리자 로그인, 권한 분리, 기존 방송/후원 내역 조회
- 수동 후원 한 건 입력, 같은 요청 재전송 시 중복 방지
- 계좌/투네 수집 한 건, 보류→승인, 분배와 펀딩 반영
- OBS 알림 단독 재생, 두 플레이어 중복 재생 방지
- 프리셋·룰렛·미션 타이머·설정 저장 및 새로고침
- 가계부와 기존 증빙 다운로드

`/api/health`의 `storage: "postgres"`는 연결 방식 선택을 뜻하며 실제 DB 접속 성공을 보장하지 않습니다. 위 테스트와 데이터 비교가 필요합니다.

확인 후 수집/자동채팅을 켭니다. 원본 Supabase는 당장 삭제하지 말고 백업과 함께 유지하세요. Neon에 새 입력을 받기 시작한 뒤 원본으로 되돌리려면 새로 생긴 데이터도 이전해야 합니다. 단순히 `DATABASE_URL`만 지우면 최신 데이터가 누락될 수 있습니다.

## 검증 기록

- 신규 테스트 6개 통과: 실제 PostgreSQL 엔진(PGlite)에서 JSON/복합키/필터/함수 호출, 펀딩 원자성, 후원 중복 방지, 알림 소유권, 캐시 무효화, 서명 증빙 다운로드.
- 서버 시작 및 health/build/login HTTP 확인 통과.
- 기존 `npm test`: 원본과 수정본 모두 동일하게 28개 중 20개 통과, 8개 실패. 기존 테스트의 누락된 파일/낡은 기대값 문제가 있어 전체 테스트가 통과했다고 표시하지 않았습니다.
- Windows PowerShell 백업·복원 스크립트는 이 Linux 환경에서 실행 검증하지 못했습니다.
- 실제 Supabase/Neon 계정 연결, 운영 데이터 백업/복원 및 실제 방송 동작 검증은 아직 하지 않았습니다.
